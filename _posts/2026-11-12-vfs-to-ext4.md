VFS(Virtual File System)最容易被讲成一张"分层图":系统调用在最上面,ext4 在最下面,中间是 VFS。但真正让这套结构运转起来的,并不是分层本身,而是 C 语言里一种非常克制的"面向对象":**用结构体表示对象,用函数指针表表示虚函数,用引用计数和缓存管理对象生命周期**。理解了这一点,再看 `open()`、`read()` 如何一路落到 ext4,就不会觉得是魔法,而是一连串可以被逐行追踪的间接调用。

本文沿着 v7.4.0-rc1 的源码,从四个核心对象和五组操作表出发,走完"挂载 → 路径解析 → 打开 → 读写 → 回写"的完整链路,最后讨论 VFS 的设计取舍。


## 一、VFS 是一套"用 C 写的对象系统"

在 C++ 里,接口通常写作抽象基类,具体实现通过虚函数表分发。C 没有类和虚函数,但内核用三样东西拼出了等价能力:

- **对象**:`super_block`、`inode`、`dentry`、`file` 这样的结构体
- **虚函数表**:`super_operations`、`inode_operations`、`dentry_operations`、`file_operations`、`address_space_operations`
- **构造函数/析构函数**:`alloc_inode`、`fill_super`、`d_alloc`、`fput` 等回调

VFS 本身并不关心数据究竟放在 ext4、XFS 还是 tmpfs 上。它只要求具体文件系统提供一组符合约定的函数指针,然后把"上层语义"翻译成"下层回调"。这种设计的关键不在于炫技,而在于**把变化隔离在 ops 表里**:新增一个文件系统,不需要修改 `vfs_read`,只需要实现自己的 `read_iter`。

为什么不直接用 C++?内核的选择有现实原因:一是 C 的 ABI 更稳定,结构体布局和函数调用约定更容易跨编译器、跨架构控制;二是内核需要精确掌握内存布局与初始化时机,构造函数、异常、RTTI 都会增加不可控因素;三是 ops 表本身已经足够表达多态,不需要语言层面的继承。换句话说,内核不是"不会用 C++",而是用更小的语言子集实现了同样的抽象。

## 二、四个核心对象

四个对象分管不同粒度,彼此通过指针连接,构成一条从"文件系统实例"到"某次打开"的链:

| 对象 | 粒度 | 关键字段 | 定义位置 |
|---|---|---|---|
| `super_block` | 一个已挂载的文件系统实例 | `s_op`、`s_root`、`s_inodes`、`s_dentry_lru` | `include/linux/fs/super_types.h:142` |
| `inode` | 一个文件/目录的元数据 | `i_op`、`i_fop`、`i_mapping`、`i_sb` | `include/linux/fs.h:762` |
| `dentry` | 一个路径分量(名字到 inode 的绑定) | `d_name`、`d_parent`、`d_inode`、`d_op` | `include/linux/dcache.h:93` |
| `file` | 一次 `open()` 产生的打开实例 | `f_op`、`f_mapping`、`f_path` | `include/linux/fs.h:1257` |

几个容易混淆的点:

- `super_block` 描述"这块磁盘上的文件系统",它和挂载点不是一回事。同一个 `super_block` 可以被挂载多次(`bind mount`),而一个挂载点也可以被后来的挂载覆盖。
- `inode` 描述"文件本身",同一个文件可以有多个 `dentry`(硬链接),但通常只有一个 `inode`。
- `dentry` 描述"名字",它既可能是目录,也可能是普通文件,还可能是**负 dentry**(名字不存在,用于加速失败查找)。
- `file` 描述"这一次打开",同一个 `inode` 被打开两次会产生两个 `file`,各自维护偏移量 `f_pos` 和打开标志。

因此,`file->f_path.dentry->d_inode` 这条链不是冗余,而是分别回答"哪次打开、哪个名字、哪个文件"三个问题。

## 三、五组操作表

VFS 的"虚函数"按对象拆成五组。每一组都是一张静态的、通常为 `const` 的函数指针表:

| 操作表 | 挂在哪里 | 典型回调 | ext4 实例 |
|---|---|---|---|
| `super_operations` | `sb->s_op` | `alloc_inode`、`evict_inode`、`sync_fs` | `ext4_sops` |
| `inode_operations` | `inode->i_op` | `lookup`、`create`、`unlink`、`setattr` | `ext4_dir_inode_operations` |
| `dentry_operations` | `dentry->d_op` | `d_revalidate`、`d_hash`、`d_compare` | 多数文件系统用默认实现 |
| `file_operations` | `file->f_op` | `open`、`read_iter`、`write_iter`、`mmap` | `ext4_file_operations` |
| `address_space_operations` | `inode->i_mapping->a_ops` | `read_folio`、`writepages`、`dirty_folio` | `ext4_aops` |

结构体定义分别在 `include/linux/fs/super_types.h:83`、`include/linux/fs.h:2000`、`include/linux/dcache.h:162`、`include/linux/fs.h:1922`、`include/linux/fs.h:401`。

以 ext4 为例,它的文件操作表长这样(`fs/ext4/file.c:1053`):

```c
const struct file_operations ext4_file_operations = {
        .llseek         = ext4_llseek,
        .read_iter      = ext4_file_read_iter,
        .write_iter     = ext4_file_write_iter,
        .iopoll         = iocb_bio_iopoll,
        .unlocked_ioctl = ext4_ioctl,
        .mmap_prepare   = ext4_file_mmap_prepare,
        .open           = ext4_file_open,
        .release        = ext4_release_file,
        .fsync          = ext4_sync_file,
        .splice_read    = ext4_file_splice_read,
        .fallocate      = ext4_fallocate,
        .setlease       = generic_setlease,
};
```

而地址空间操作表在 `fs/ext4/inode.c:4567` 定义,`ext4_aops` 里的 `read_folio`、`writepages`、`dirty_folio` 分别对应页缓存的读入、回写和置脏。

这套做法的妙处是:**对象只需要知道自己那张表,不需要知道调用者是谁**。`vfs_read` 拿到 `file`,只做 `file->f_op->read_iter(...)`;至于这个指针指向 ext4、XFS 还是 FUSE,它一概不关心。一次间接调用,就把"通用语义"和"具体实现"分开了。

## 四、挂载:从 mount() 到 ext4_fill_super

挂载是理解 VFS 的第一道关口。很多资料把它简化成"把设备挂到目录上",但在内核里,它实际上做了三件事:

1. 解析文件系统类型,建立 `fs_context`
2. 创建或复用 `super_block`
3. 让具体文件系统填充超级块,并产生根 dentry

`ext4_get_tree` 只有一行(`fs/ext4/super.c:5929`):

```c
static int ext4_get_tree(struct fs_context *fc)
{
        return get_tree_bdev(fc, ext4_fill_super);
}
```

`get_tree_bdev` 的关键逻辑在 `fs/super.c:1789` 的 `get_tree_bdev_flags`:

```c
s = sget_dev(fc, dev);
if (IS_ERR(s))
        return PTR_ERR(s);

if (s->s_root) {
        /* 已存在:复用,不重新 fill_super */
        if ((fc->sb_flags ^ s->s_flags) & SB_RDONLY) {
                deactivate_locked_super(s);
                return -EBUSY;
        }
} else {
        error = setup_bdev_super(s, fc->sb_flags, fc);
        if (!error)
                error = fill_super(s, fc);
        if (error) {
                deactivate_locked_super(s);
                return error;
        }
        s->s_flags |= SB_ACTIVE;
}
```

这段代码说明了两件事:

- **super_block 是按设备去重的**。同一块设备重复挂载,通常复用已有的 `super_block`,不会重新读超级块。这也是为什么"挂载两次"通常不会让文件系统被初始化两次。
- **`fill_super` 只在新超级块上调用**。ext4 的 `ext4_fill_super` 负责读 `ext4_super_block`、校验块组描述符、加载日志、初始化 `ext4_sb_info`,最后用 `ext4_iget(EXT4_ROOT_INO, ...)` 拿到根 inode,再用 `d_make_root` 生成 `sb->s_root`(`fs/ext4/super.c:5664`、`5679`)。

挂载完成后,`do_new_mount_fc`(`fs/namespace.c:3906`)把 `vfsmount` 加入当前挂载命名空间的挂载树。**命名空间决定"谁能看见这棵树",super_block 决定"这棵树背后是哪份文件系统"**,两者的粒度不同,这也是容器可以共享同一个 super_block、却拥有不同挂载视图的原因。

## 五、路径解析:dentry 缓存是主战场

`open("/home/ruy/file")` 的第一件事不是打开文件,而是把路径逐段解析成 dentry。入口在 `path_openat`(`fs/namei.c:4996`):

```c
file = alloc_empty_file(op->open_flag, current_cred());
...
const char *s = path_init(nd, flags);
while (!(error = link_path_walk(s, nd)) &&
       (s = open_last_lookups(nd, file, op)) != NULL)
        ;
if (!error)
        error = do_open(nd, file, op);
```

`path_init`(`fs/namei.c:2683`)确定起点(根目录、当前工作目录或 `dirfd`),`link_path_walk`(`fs/namei.c:2584`)负责逐段推进,每个普通分量最终交给 `walk_component`(`fs/namei.c:2271`):

```c
dentry = lookup_fast(nd);
if (IS_ERR(dentry))
        return ERR_CAST(dentry);
if (unlikely(!dentry)) {
        dentry = lookup_slow(&nd->last, nd->path.dentry, nd->flags);
        if (IS_ERR(dentry))
                return ERR_CAST(dentry);
}
...
return step_into(nd, flags, dentry);
```

`lookup_fast`(`fs/namei.c:1849`)是快路径。它优先在 RCU 模式下查 dcache:

```c
if (nd->flags & LOOKUP_RCU) {
        dentry = __d_lookup_rcu(parent, &nd->last, &nd->next_seq);
        if (unlikely(!dentry)) {
                if (!try_to_unlazy(nd))
                        return ERR_PTR(-ECHILD);
                return NULL;
        }
        if (read_seqcount_retry(&parent->d_seq, nd->seq))
                return ERR_PTR(-ECHILD);
        ...
}
```

这里出现了两个关键机制:

- **RCU 查找**:`__d_lookup_rcu`(`fs/dcache.c:2560`)在无锁情况下遍历哈希桶,靠 `d_seq` 序列号检测并发修改。失败时返回 `-ECHILD`,退回到带锁的慢路径。
- **seqlock 校验**:父 dentry 的 `d_seq` 在 rename 等操作期间会变化,读到一半发现序列号变了,就必须重来。

快路径没有命中时,`walk_component` 会调用 `lookup_slow`,它在共享 inode 锁下再进入 `__lookup_slow`(`fs/namei.c:1899`):

```c
dentry = d_alloc_parallel(dir, name);
...
old = inode->i_op->lookup(inode, dentry, flags);
d_lookup_done(dentry);
```

最后这句 `inode->i_op->lookup` 就是 VFS 把控制权交给具体文件系统的地方。对 ext4,它指向 `ext4_lookup`(`fs/ext4/namei.c:1762`):

```c
static struct dentry *ext4_lookup(struct inode *dir, struct dentry *dentry,
                                  unsigned int flags)
{
        struct inode *inode;
        struct ext4_dir_entry_2 *de = NULL;
        struct buffer_head *bh;

        if (dentry->d_name.len > EXT4_NAME_LEN)
                return ERR_PTR(-ENAMETOOLONG);

        bh = ext4_lookup_entry(dir, dentry, &de);
        if (IS_ERR(bh))
                return ERR_CAST(bh);
        inode = NULL;
        if (bh) {
                __u32 ino = le32_to_cpu(de->inode);
                brelse(bh);
                ...
                inode = ext4_iget(dir->i_sb, ino, EXT4_IGET_NORMAL);
                ...
        }
        return d_splice_alias(inode, dentry);
}
```

`ext4_lookup_entry`(`fs/ext4/namei.c:1691`)在目录项里按名字查找,ext4 会走 htree 索引;找到后拿到 inode 号,`ext4_iget` 再从磁盘读入 inode(如果 inode 缓存里已有,则直接复用)。如果名字不存在,ext4 返回 `NULL`,VFS 会把这个 dentry 标记为负 dentry 并放入缓存,下一次同样的失败查找就不用再进文件系统。

## 六、打开:vfs_open 与 f_op->open

路径解析完成后,`do_open`(`fs/namei.c:4796`)做权限、`O_TRUNC`、`O_CREAT` 等处理,最后调用 `vfs_open`(`fs/open.c:1101`):

```c
int vfs_open(const struct path *path, struct file *file)
{
        int ret;

        file->__f_path = *path;
        path_get(&file->f_path);
        ret = do_dentry_open(file, NULL);
        if (!ret)
                fsnotify_open(file);
        return ret;
}
```

`do_dentry_open`(`fs/open.c:939`)是真正把 `file` 和 `inode` 绑起来的地方。它做了一件非常重要的事:

```c
f->f_op = fops_get(inode->i_fop);
...
if (!open)
        open = f->f_op->open;
if (open) {
        error = open(inode, f);
        if (error)
                goto cleanup_all;
}
f->f_mode |= FMODE_OPENED;
```

也就是说,**`file->f_op` 来自 `inode->i_fop`**,而 `inode->i_fop` 是在 inode 建立时按文件类型设置的。对普通文件,ext4 在 `ext4_set_inode_operations` 附近把它设为 `ext4_file_operations`(`fs/ext4/inode.c:6500`)。之后如果文件系统实现了 `.open`,就会调用 `ext4_file_open`(`fs/ext4/file.c:980`)。

注意 `vfs_open` 并不直接调用 ext4 的某个函数,它只认 `f_op->open`。这就是接口与实现的分离:VFS 只负责"打开这个动作的通用部分",具体文件系统负责"打开时还要做什么"。

## 七、读:vfs_read 如何落到 filemap_read

读路径的骨架在 `vfs_read`(`fs/read_write.c:554`):

```c
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
        ...
        if (!(file->f_mode & FMODE_READ))
                return -EBADF;
        if (!(file->f_mode & FMODE_CAN_READ))
                return -EINVAL;
        ...
        if (file->f_op->read)
                ret = file->f_op->read(file, buf, count, pos);
        else if (file->f_op->read_iter)
                ret = new_sync_read(file, buf, count, pos);
        else
                ret = -EINVAL;
        ...
}
```

现代文件系统基本都实现 `read_iter`,`read` 只是历史兼容。`new_sync_read`(`fs/read_write.c:483`)把用户缓冲区包装成 `iov_iter`,构造 `kiocb`,再调用 `filp->f_op->read_iter`:

```c
init_sync_kiocb(&kiocb, filp);
kiocb.ki_pos = (ppos ? *ppos : 0);
iov_iter_ubuf(&iter, ITER_DEST, (void __user *)buf, len);
ret = filp->f_op->read_iter(&kiocb, &iter);
```

对 ext4,这个指针是 `ext4_file_read_iter`(`fs/ext4/file.c:132`):

```c
static ssize_t ext4_file_read_iter(struct kiocb *iocb, struct iov_iter *to)
{
        struct inode *inode = file_inode(iocb->ki_filp);

        if (unlikely(ext4_forced_shutdown(inode->i_sb)))
                return -EIO;
        if (!iov_iter_count(to))
                return 0;
        if (iocb->ki_flags & IOCB_DIRECT)
                return ext4_dio_read_iter(iocb, to);
        return generic_file_read_iter(iocb, to);
}
```

非 DAX、非 Direct IO 的普通读,进入 `generic_file_read_iter`(`mm/filemap.c:3004`),最终落到 `filemap_read`(`mm/filemap.c:2816`):

```c
do {
        cond_resched();
        if (unlikely(iocb->ki_pos >= i_size_read(inode)))
                break;

        error = filemap_get_pages(iocb, iter->count, &fbatch, false);
        if (error < 0)
                break;

        isize = i_size_read(inode);
        ...
        copied = copy_folio_to_iter(folio, offset, bytes, iter);
} while (iov_iter_count(iter));
```

`filemap_get_pages`(`mm/filemap.c:2715`)负责在页缓存里找 folio;命中就直接返回,未命中则分配 folio 并通过 `read_folio` 触发回读。ext4 的 `read_folio` 是 `ext4_read_folio`(`fs/ext4/readpage.c:321`),它会把磁盘块读进页缓存,必要时调用 `ext4_mpage_readpages` 和 `submit_bio` 提交块层 IO。

把这条链压缩成一句:

```text
vfs_read → f_op->read_iter → ext4_file_read_iter
→ generic_file_read_iter → filemap_read → filemap_get_pages
→ a_ops->read_folio → ext4_read_folio → submit_bio
```

## 八、写与回写:先写缓存,再延迟落盘

写路径与读路径对称,但多了一层"脏页"语义。`vfs_write`(`fs/read_write.c:667`)同样检查 `FMODE_WRITE`,然后调用 `write` 或 `write_iter`。ext4 的写入口是 `ext4_file_write_iter`(`fs/ext4/file.c:785`):

```c
if (iocb->ki_flags & IOCB_DIRECT)
        return ext4_dio_write_iter(iocb, from);
else
        return ext4_buffered_write_iter(iocb, from);
```

缓冲写进入 `ext4_buffered_write_iter`(`fs/ext4/file.c:348`),它在 `inode_lock` 保护下做扩展检查和 `generic_perform_write`(`fs/ext4/file.c:372`):

```c
inode_lock(inode);
inode_dio_wait(inode);

ret = ext4_write_checks(iocb, from);
if (ret <= 0)
        goto out;

if (ext4_inode_buffered_iomap(inode))
        ret = ext4_iomap_buffered_write(iocb, from);
else
        ret = generic_perform_write(iocb, from);

out:
inode_unlock(inode);
```

`generic_perform_write` 通过 `a_ops->write_begin` 把页准备好,由 `a_ops->write_end` 标记为脏。ext4 的延迟分配模式使用 `ext4_da_write_begin`/`ext4_da_write_end`(`fs/ext4/inode.c:3263`、`3418`)。这时数据只是在页缓存里,**`write()` 返回并不等于已经落盘**。

真正把脏页写到磁盘的是回写路径。内核的 flusher 或 `sync`/`fsync` 最终调用 `do_writepages`(`mm/page-writeback.c:2551`),由它分派到 `mapping->a_ops->writepages`:

`ext4_writepages` 本身只是外层包装,负责取 `s_writepages_rwsem` 读锁并处理 `data=journal` 的二次回写:

```c
static int ext4_writepages(struct address_space *mapping,
                           struct writeback_control *wbc)
{
        ...
        alloc_ctx = ext4_writepages_down_read(sb);
        ret = ext4_do_writepages(&mpd);
        if (!ret && mpd.journalled_more_data)
                ret = ext4_do_writepages(&mpd);
        ext4_writepages_up_read(sb, alloc_ctx);
        return ret;
```

对 ext4 来说,回写还要经过日志(jbd2)和 extent 映射。`ext4_map_blocks` 负责把逻辑块翻译成物理块,必要时分配新块并写入 extent 树;`ext4_io_submit` 把 bio 交给块层。**读路径是"页缓存未命中才读盘",写路径是"先写页缓存,合适的时候再批量落盘"**,这种不对称正是文件系统性能的关键。

## 九、三层缓存:dcache、inode cache、page cache

VFS 的性能很大程度上来自三层缓存,它们各自解决不同问题:

| 缓存 | 缓存什么 | 数据结构 | 命中后省掉什么 |
|---|---|---|---|
| dentry cache | 名字 → dentry | 哈希表 + LRU 链表 | 目录项查找、磁盘 IO |
| inode cache | inode 号 → inode | `inode_hashtable` + 每 sb 链表 | 读 inode、解析元数据 |
| page cache | 文件偏移 → folio | `address_space->i_pages`(xarray) | 读磁盘、重复 IO |

**dcache** 的哈希表由 `rename_lock` 和每个 dentry 的 `d_seq` 保护(`fs/dcache.c:87`),查找时可以在 RCU 模式下无锁进行。未被引用的 dentry 会进入 `s_dentry_lru`(`include/linux/fs/super_types.h:267`),内存紧张时被回收。负 dentry 也在这里,它让"文件不存在"这个结论同样可以缓存。

**inode cache** 以 `inode_hashtable`(`fs/inode.c:61`)为主索引,`iget_locked`(`fs/inode.c:1461`)会先查 `find_inode_fast`(`fs/inode.c:1080`),找到就增加引用;找不到才分配新 inode 并标记 `I_NEW`,等文件系统把磁盘内容填进来。每个 `super_block` 还维护 `s_inodes` 和 `s_inode_lru`(`include/linux/fs/super_types.h:281`、`268`),用于回写和回收。

**page cache** 挂在 `address_space` 上,`i_pages` 是一个 xarray(`include/linux/fs.h:471`),用 `DIRTY`、`WRITEBACK`、`TOWRITE` 等标签管理页状态。读命中时,`filemap_read` 直接 `copy_folio_to_iter`,完全不进块层;写命中时,只改页缓存并置脏。只有未命中或回写时,才真正和磁盘打交道。

三层缓存是**串联**的:路径解析命中 dcache,就不需要进文件系统;进了文件系统,命中 inode cache 就不需要读 inode;真正读数据时,命中 page cache 就不需要读磁盘。任何一层命中,都能把后面的成本省掉。这也是为什么"文件系统快不快"不能只看磁盘,还要看缓存命中率。

从生命周期看,三层缓存的回收压力是自下而上的。page cache 受 `dirty_ratio` 和内存回收控制;inode 在最后一个 dentry 断开且没有引用后进入 `s_inode_lru`;dentry 则在 `dput` 把引用降到零后进入 `s_dentry_lru`。内核用 `shrink_slab` 和 `super_cache_scan` 按内存压力回收它们,而不是"用完立刻释放"。这种延迟释放换来了复用率,也让"打开过的文件再打开一次"通常只需要一次哈希查找。代价是内存占用和回收时机的调优空间:缓存太大浪费内存,太小又退化成频繁 IO。

## 十、ext4 在磁盘上长什么样

VFS 把 ext4 当成一组回调,但 ext4 自己仍然要理解磁盘布局。ext4 把设备划分成若干个**块组**,每个块组有独立的块位图、inode 位图和 inode 表;超级块和块组描述符记录全局信息。

关键结构:

- `struct ext4_super_block`(`fs/ext4/ext4.h:1372`):块数、inode 数、每块组块数、magic 等
- `struct ext4_group_desc`(`fs/ext4/ext4.h:402`):块位图、inode 位图、inode 表位置
- `struct ext4_inode`(`fs/ext4/ext4.h:794`):`i_block[EXT4_N_BLOCKS]` 保存数据块或 extent 树根
- `struct ext4_extent_header`/`ext4_extent`(`fs/ext4/ext4_extents.h:78`、`56`):extent 树的节点与叶子

当 inode 设置了 `EXT4_EXTENTS_FL`(`fs/ext4/ext4.h:503`),`i_block` 里放的就是 extent 树根,而不是 12 个直接块指针。extent 用"起始逻辑块 + 长度 + 起始物理块"描述一段连续区域,比传统的三级间接块更适合大文件。`ext4_map_blocks`(`fs/ext4/inode.c:772`)就是把这棵树翻译成物理块的核心函数。

## 十一、设计精妙:四个值得借鉴的决定

**第一,接口与实现分离。** VFS 不定义"文件系统应该怎么存数据",只定义"文件系统应该响应哪些操作"。`vfs_read` 不知道 ext4 的 extent,也不需要知道。新增文件系统时,只要填好 ops 表,就能接入整套系统调用。

**第二,ops 表就是虚函数表。** 每个对象只持有指向自己实现的一组函数指针,调用是一次间接跳转。它没有继承、没有运行时类型信息,但足够表达多态。代价是调试时调用栈多一层,好处是结构极简、缓存友好。

**第三,缓存分层。** dcache、inode cache、page cache 各自独立,又通过对象指针自然衔接。任何一层都可以被绕过(Direct IO 绕过 page cache,`O_PATH` 可以只拿路径),这让内核能针对不同场景做取舍。

**第四,mount namespace。** `super_block` 表示文件系统实例,`vfsmount` 表示挂载关系,`mnt_namespace`(`fs/mount.h:13`)表示一棵挂载树。`copy_mnt_ns`(`fs/namespace.c:4409`)让容器拥有独立的挂载视图,而底层 super_block 仍然可以共享。这种"数据与视图分离"的设计,是容器文件系统的基础。

**第五,错误也走统一通道。** VFS 大量使用 `ERR_PTR` 传递错误指针,而不是为每个回调设计额外的错误码出参。`lookup` 返回 `ERR_PTR(-ENOENT)` 还是 `NULL`,语义清晰;负 dentry 则把"不存在"也变成一种可缓存的结果。统一错误表示让层层回调的代码不必到处写 `if (ret < 0)` 和出参检查,也减少了漏判错误的可能。

把这些决定放在一起看,会发现 VFS 的"面向对象"并不追求语言特性,而是追求**边界清晰**:对象负责状态,ops 负责行为,缓存负责性能,命名空间负责视图。每一层都只依赖下一层的接口,而不是下一层的实现。这正是它能同时容纳 ext4、XFS、Btrfs、FUSE 和数十种文件系统的原因。

```bash
# 当前挂载与文件系统类型
```

调试路径问题时,先分清是 dcache 未命中、inode 读取,还是 page cache 未命中。`perf` 看调用栈、`/proc/slabinfo` 看缓存规模、`bpftrace` 看具体参数,通常比盲猜有效。

## 十三、常见误解

- **"VFS 是一个文件系统"**:VFS 是抽象层,不是存储实现。
- **"dentry 就是目录"**:dentry 是"名字",可以是文件、目录、符号链接,甚至是负项。
- **"inode cache 就是 page cache"**:前者缓存元数据,后者缓存文件内容。
- **"write() 返回就落盘了"**:缓冲写只到页缓存,落盘由回写和 `fsync` 决定。
- **"ext4_file_operations 每个文件一份"**:它是静态 `const` 表,所有文件共享。
- **"挂载会复制文件系统"**:通常只是创建/复用一个 super_block 和挂载关系。
